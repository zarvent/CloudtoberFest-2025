De Zero a Alta disponibilidad para HTTP con Terraform y AWS

🎙️voice memo
📰 briefing doc simplified

Este documento resume un proyecto práctico sobre cómo crear un sistema web que funcione sin interrupciones. El proyecto usa Terraform (una herramienta para automatizar la creación de infraestructura) y Amazon Web Services (AWS). El problema que resuelve es simple: crear y configurar manualmente todos los recursos necesarios es complicado, toma mucho tiempo y es fácil cometer errores. La solución automatiza todo este trabajo usando código de Terraform que maneja los componentes de AWS. El proyecto se basa en tres ideas principales: copiar recursos (tener múltiples servidores), repartir la carga entre los servidores y tener respaldos listos para cuando algo falle. El sistema usa un balanceador de carga de aplicaciones, grupos de destino y un grupo de autoescalado que ajusta automáticamente la cantidad de servidores según el uso de CPU. Las pruebas demostraron que el sistema funciona: detecta cuando hay mucha actividad, activa alarmas y crea más servidores automáticamente cuando es necesario.

1. Por qué es importante que los servicios siempre funcionen

Mantener un servicio funcionando casi todo el tiempo es fundamental para cualquier negocio moderno. Esto significa que el servicio debe estar disponible y ser confiable para los clientes la mayor parte del tiempo posible. Su importancia es clara: garantiza que el negocio siga operando sin interrupciones, evitando problemas que afectan los ingresos y la confianza de los clientes.

IBM lo define así:

"La alta disponibilidad es lograr que un servicio esté funcionando y sea confiable para los clientes, no necesariamente el 100% del tiempo, pero la mayor parte del tiempo posible".

2. Tres técnicas clave usadas en el proyecto

Para lograr que el servicio funcione sin interrupciones, el proyecto usó tres técnicas importantes:

  • Copiar recursos: Crear varias copias de un servidor (como una instancia EC2) a partir de una plantilla. Así hay múltiples servidores idénticos listos para atender solicitudes.
  • Repartir la carga: Distribuir el tráfico web entre varios servidores. El objetivo es que ningún servidor se sobrecargue y todos funcionen de manera óptima.
  • Tener respaldos: Mantener un sistema de respaldo inactivo mientras el sistema principal funciona. Si el sistema principal falla, el sistema de respaldo se activa automáticamente para que el servicio no se detenga.

3. El problema: hacerlo manualmente es muy complicado

Implementar estas técnicas de forma manual presenta grandes desafíos. Hay que crear, conectar y configurar muchos recursos—un proceso que consume mucho tiempo y es fácil cometer errores.

El mayor problema surge al copiar la infraestructura en diferentes ambientes (por ejemplo, de un ambiente de prueba a otro). Este trabajo repetitivo es tedioso y no se puede escalar fácilmente.

4. La solución: automatizar todo con Terraform

Para resolver los problemas de la gestión manual, el proyecto usó un enfoque llamado Infraestructura como Código con Terraform. Esta herramienta permite automatizar la creación y gestión de toda la infraestructura usando código.

Ventajas de usar Terraform

  • Fácil de leer: La sintaxis es clara e intuitiva, fácil de entender.
  • Control de cambios: Terraform compara lo que tienes actualmente con lo que quieres crear. Antes de hacer cambios, muestra un plan detallado de lo que va a crear, modificar o eliminar.
  • Historial de versiones: El código de Terraform se puede guardar en sistemas como Git, permitiendo trabajar en equipo, ver el historial de cambios y volver a versiones anteriores si es necesario.
  • Código reutilizable: El proyecto se organizó usando módulos (como funciones) que agrupan recursos relacionados. Esto permite reutilizar código y mantener todo organizado.

5. Componentes principales del proyecto en AWS

El código de Terraform controla varios recursos importantes en AWS:

ComponenteQué hace
Balanceador de Carga (ALB)Recibe el tráfico web y lo reparte entre los servidores disponibles.
Grupo de DestinoAgrupa los servidores EC2 que están listos para recibir tráfico. Se actualiza automáticamente cuando se crean o eliminan servidores.
Grupo de Autoescalado (ASG)El recurso más importante. Gestiona los servidores EC2: crea nuevos cuando se necesitan y elimina los que no se usan.
Políticas de EscaladoReglas que definen cuándo crear o eliminar servidores. En este proyecto, se basan en métricas como el uso de CPU.
Alarmas de CloudWatchMonitorean métricas (como el uso de CPU) y activan las políticas de escalado cuando se superan ciertos límites.
Recursos de RedIncluye componentes básicos como VPC, Subnets y Security Groups que proporcionan la red y seguridad necesarias.

6. Cómo funciona el escalado automático

El sistema funciona mediante un ciclo automatizado de monitoreo y acción:

  1. Monitoreo: Se vigila constantemente una métrica, como el uso promedio de CPU. Si supera un límite (por ejemplo, más del 40% durante 3 minutos), se activa una alarma en CloudWatch.
  1. Activación de la política: La alarma envía una señal al Grupo de Autoescalado, activando la política correspondiente.
  1. Acción: El Grupo de Autoescalado ajusta la cantidad de servidores. Si hay mucha carga, crea nuevos servidores a partir de la plantilla.
  1. Actualización: El sistema actualiza automáticamente la lista de servidores disponibles en el Grupo de Destino. Esto permite que el Balanceador de Carga empiece a enviarles tráfico inmediatamente.

7. Resultados de la prueba práctica

Se probó que la solución funciona mediante una demostración:

  • Inicio: Se empezó con una cuenta de AWS vacía.
  • Despliegue: Se ejecutó el comando terraform apply, que creó toda la infraestructura automáticamente: balanceador de carga, grupo de autoescalado, grupo de destino y un servidor inicial.
  • Prueba de carga: Se usó un script para generar muchas solicitudes web al balanceador, simulando mucho tráfico.
  • Resultado:
    • Los gráficos de CloudWatch mostraron que el uso de CPU superó el 40%.
    • La alarma se activó correctamente.
    • El sistema creó automáticamente tres nuevos servidores para manejar la carga adicional.

La prueba confirmó que el sistema responde automáticamente a los cambios de carga, manteniendo el servicio funcionando.

8. Conclusiones importantes

  • Importancia crítica: Mantener los servicios funcionando es esencial para cualquier negocio con muchos clientes.
  • Valor de las pruebas: Se recomienda hacer pruebas de caos para verificar que el sistema responde bien cuando algo falla.
  • Usar servicios en la nube: Proveedores como AWS ofrecen los componentes necesarios para construir sistemas robustos.
  • Automatización vital: Herramientas como Terraform son indispensables para gestionar infraestructuras con más de 10 o 20 recursos, aportando automatización y consistencia.

Este documento sintetiza la arquitectura y hallazgos de un proyecto práctico enfocado en implementar un sistema de alta disponibilidad para servicios HTTP. Utiliza Terraform como herramienta de Infraestructura como Código (IaC) sobre Amazon Web Services (AWS). El problema central es la complejidad y naturaleza tediosa de crear y configurar manualmente los numerosos recursos necesarios para garantizar la resiliencia—un proceso ineficiente al replicar entornos. La solución propuesta automatiza este despliegue mediante un módulo de Terraform que orquesta los componentes de AWS. El proyecto se fundamenta en tres técnicas clave de alta disponibilidad: replicación de recursos, balanceo de carga para distribuir el tráfico y redundancia para asegurar la continuidad mediante sistemas de respaldo y procesos de failover. La arquitectura resultante utiliza un Application Load Balancer, Target Groups y—de manera central—un Auto Scaling Group configurado con políticas de escalado dinámico basadas en métricas como el uso de CPU. La demostración práctica validó que el sistema detecta aumentos de carga, dispara alarmas de CloudWatch y escala horizontalmente de forma automática, demostrando la viabilidad y eficiencia del enfoque IaC para construir infraestructuras robustas y autogestionadas.

1. El Imperativo de la Alta Disponibilidad

La alta disponibilidad (HA) se ha convertido en un pilar fundamental para las operaciones de negocio modernas. Se define como la capacidad de un servicio para estar disponible y ser confiable para los clientes la mayor cantidad de tiempo posible. Su importancia es crucial: garantiza la continuidad de los flujos de trabajo y procesos de negocio, evitando caídas que impactan negativamente los ingresos y la confianza del cliente.

Una cita de un post de IBM define el concepto así:

"La alta disponibilidad de los servicios es un concepto que trata de que un servicio que tú tengas que esté funcionando, que sea o que esté disponible y que sea fiable para clientes, no necesariamente el 100% del tiempo, pero la mayor cantidad de tiempo posible".

2. Técnicas Fundamentales Implementadas

Para lograr la alta disponibilidad en el proyecto, se aplicaron tres técnicas esenciales utilizadas comúnmente en la gestión de infraestructura para servicios HTTP.

  • Replicación: Crea múltiples copias de un recurso (como una instancia EC2) a partir de una plantilla. Esto asegura que existan múltiples unidades de trabajo idénticas listas para procesar solicitudes.
  • Balanceo de Carga (Load Balancing): Distribuye el tráfico de red—ya sea interno o externo—entre un conjunto de recursos o servidores backend. Su objetivo es mantener un estado operativo óptimo, evitando que un solo recurso se sobrecargue.
  • Redundancia: Mantiene un sistema secundario o de respaldo (backup) que permanece inactivo mientras el sistema principal está operativo. En caso de falla del sistema primario, se activa un proceso de conmutación por error (failover), donde el sistema secundario asume las operaciones para minimizar el tiempo de inactividad (downtime).

3. El Problema: Complejidad de la Implementación Manual

La implementación manual de estas técnicas presenta desafíos significativos. Requiere crear, conectar y configurar una gran cantidad de recursos—un proceso que no solo consume tiempo sino que también es propenso a errores humanos.

El principal punto de fricción surge al replicar la infraestructura en diferentes entornos (por ejemplo, de un entorno de staging a otro). Este trabajo repetitivo se convierte en un proceso tedioso que carece de escalabilidad y consistencia.

4. La Solución: Infraestructura como Código con Terraform

Para superar los desafíos de la gestión manual, el proyecto adoptó un enfoque de Infraestructura como Código (IaC) utilizando Terraform. Esta herramienta permite automatizar el aprovisionamiento y la gestión del ciclo de vida de la infraestructura de manera declarativa.

Ventajas de Terraform en el Proyecto

  • Lenguaje Legible por Humanos: Su sintaxis declarativa es intuitiva y facilita la comprensión de la infraestructura definida.
  • Seguimiento de Cambios: Terraform utiliza un archivo de estado para comparar la configuración actual con la infraestructura desplegada. Antes de aplicar cambios, muestra un plan detallado de lo que se creará, modificará o eliminará, proporcionando seguridad y previsibilidad.
  • Control de Versiones: El código de Terraform puede versionarse en sistemas como Git, permitiendo el trabajo colaborativo, el seguimiento del historial de cambios y la capacidad de revertir a versiones anteriores.
  • Modularidad: El proyecto se estructuró usando módulos de Terraform, que actúan como funciones reutilizables agrupando recursos relacionados (ej. networking, seguridad, balanceo de carga). Esto promueve la reutilización de código y una organización lógica de la infraestructura.

5. Arquitectura del Proyecto en AWS

El módulo de Terraform desarrollado orquesta un conjunto de recursos clave en AWS para construir la arquitectura de alta disponibilidad.

Recurso PrincipalDescripción y Función
Application Load Balancer (ALB)Recibe el tráfico HTTP externo y lo distribuye a las instancias disponibles.
Target GroupActúa como un pivote, agrupando las instancias EC2 disponibles para recibir tráfico del ALB. Es actualizado dinámicamente por el Auto Scaling Group.
Auto Scaling Group (ASG)Considerado el recurso más importante del proyecto, gestiona el ciclo de vida de las instancias EC2. Se encarga de la replicación (crear nuevas instancias) y la reducción (terminar instancias innecesarias) de forma automática.
Scaling PoliciesPolíticas de escalamiento que definen las condiciones bajo las cuales el ASG debe actuar. En este proyecto, se utilizó un método de escaladodinámico basado en métricas.
CloudWatch AlarmsMonitorean métricas específicas (como el uso de CPU) y actúan como disparadores (triggers) para las políticas de escalado cuando se superan los umbrales definidos.
Recursos de RedIncluye componentes estándar como VPC, Subnets y Security Groups para proporcionar el entorno de red y seguridad necesario.

6. Mecanismo de Autoescalado Dinámico: Flujo de Operación

El núcleo funcional del sistema se basa en un ciclo de retroalimentación automatizado entre el monitoreo y la acción, orquestado por varios servicios de AWS.

  1. Monitoreo y Detección: Una métrica, como el promedio de uso de CPU de las instancias, es monitoreada continuamente. Si supera un umbral predefinido (ej. >40% durante 3 minutos), se activa una alarma de CloudWatch.
  1. Disparo de la Política: La alarma de CloudWatch envía una señal al Auto Scaling Group, activando la política de escalado correspondiente.
  1. Acción de Escalado: El Auto Scaling Group, usando sus algoritmos internos, ajusta la cantidad de instancias. En caso de alta carga, aprovisiona nuevas instancias a partir de la plantilla definida para escalar horizontalmente (scale out).
  1. Actualización del Balanceador: El ASG actualiza automáticamente la lista de instancias disponibles en el Target Group. Esto informa al Application Load Balancer sobre las nuevas instancias saludables, permitiéndole comenzar a dirigirles tráfico de inmediato.

7. Resultados de la Demostración Práctica

La efectividad de la solución fue validada mediante una demostración en vivo que siguió estos pasos:

  • Estado Inicial: Se partió de una cuenta de AWS sin recursos preexistentes.
  • Despliegue con Terraform: Se ejecutó el comando terraform apply, que aprovisionó toda la infraestructura definida en el código: un ALB, un ASG, un Target Group y una instancia EC2 inicial (configurada como el estado deseado al inicio).
  • Prueba de Estrés: Se utilizó un script para generar una carga constante de solicitudes HTTP al ALB, simulando un aumento de tráfico.
  • Respuesta del Sistema:
    • Los gráficos de CloudWatch mostraron que el uso de CPU de la instancia superó el umbral del 40%.
    • La alarma de CloudWatch se disparó correctamente.
    • La política de escalado se activó, y el Auto Scaling Group creó automáticamente tres nuevas instancias para manejar la carga adicional.

La demostración confirmó que la arquitectura reacciona autónomamente a las condiciones de carga, manteniendo la disponibilidad del servicio.

8. Conclusiones y Lecciones Clave

  • Criticidad de la Alta Disponibilidad: Es una práctica esencial para cualquier negocio con una base de clientes considerable, garantizando la continuidad y la confianza.
  • Importancia de las Pruebas: Se recomienda realizar "pruebas del caos" (chaos testing) para predecir el comportamiento del sistema ante fallos y validar la resiliencia de la arquitectura.
  • Aprovechamiento de Servicios Cloud: Los proveedores como AWS ofrecen los componentes necesarios ("building blocks") para construir sistemas de alta disponibilidad complejos.
  • El Papel Vital de IaC: Herramientas como Terraform son indispensables para gestionar infraestructuras con más de 10 o 20 recursos, aportando automatización, consistencia y escalabilidad al proceso.
